> FP·금액 관련 코드를 바꾸기 전에 이 문서를 읽는다. 기준값은 코드가 아니라

## 2. 기준 버전 (`backend/app/standards/`)

| 버전 ID | 내용 | 상태 |
|---|---|---|
| `KOSA-FORM-2024G-241231` | 위 1101/1102 양식에서 추출한 값 | 가중치·복잡도표·보정계수표·규모식: 양식 수식 확인 / 단가: 양식 기재값 / 이윤율: 양식 예시 입력값(미확인) / VAT: 타 양식의 ×1.1 확인 / 끝수·단계비율: 미확인(사용자 설정) |

견적 버전은 산정 시점의 기준 JSON 전체를 스냅샷으로 저장한다(나중에 기준 파일이 바뀌어도 과거 견적 보존).

## 3. 간이법 (구현: `backend/app/fp/engine.py::calc_simple`)
- 근거: 1101 양식 `FP산정(간이법)!G5` 수식
  `IF(F="EI",4, "EO",5.2, "EQ",3.9, "ILF",7.5, "EIF",5.4)`
- 유형별 평균 가중치: **ILF 7.5, EIF 5.4, EI 4.0, EO 5.2, EQ 3.9** (복잡도 판정 없음)
- 총 FP = Σ 가중치 (양식 `SW개발비 산정!E30:J30` SUMIF 합계와 동일)
- DET/FTR/RET 입력이 없어도 유형만 확정되면 계산된다.

## 4. 정통법 (구현: `calc_detailed`)
- 근거: 1102 양식 VBA `FPR(TType, FTR, DET)`, `FPV(TType, FPRating)`
- 복잡도 판정표(양식 VBA 그대로, IFPUG 표와 동일 구조)

EI (FTR × DET)
| FTR \ DET | 1–4 | 5–15 | 16+ |
|---|---|---|---|
| 0–1 | L | L | A |
| 2 | L | A | H |
| 3+ | A | H | H |

EO·EQ (FTR × DET)
| FTR \ DET | 1–5 | 6–19 | 20+ |
|---|---|---|---|
| 0–1 | L | L | A |
| 2–3 | L | A | H |
| 4+ | A | H | H |

ILF·EIF (RET × DET)
| RET \ DET | 1–19 | 20–50 | 51+ |
|---|---|---|---|
| 1 | L | L | A |
| 2–5 | L | A | H |
| 6+ | A | H | H |

- 가중치(L/A/H): **EI 3/4/6, EO 4/5/7, EQ 3/4/6, ILF 7/10/15, EIF 5/7/10**
- 입력 검증(양식과 다른 점, 의도적): 양식 VBA는 DET=0 등에서 빈 값을 반환한다.
  본 시스템은 DET 미입력·0, 데이터 기능 RET 미입력·0, 트랜잭션 FTR 미입력이면 **'미확정(입력 누락)'**으로 두고 점수에 넣지 않는다.
  사용자가 명시적 가정 복잡도(`assumed_complexity` + 가정 사유)를 입력하면 '가정 적용'으로 계산하고 표시한다.

## 5. 개발비 (구현: `backend/app/fp/cost.py`)
- 근거: 1101/1102 양식 `SW개발비 산정` 시트
  - 개발원가 = 총FP × FP당 단가 × 규모 × 연계복잡성 × 성능 × 운영환경 × 보안성 (`K7=PRODUCT(B7:J7)`)
  - 이윤 = 개발원가 × 이윤율 (`K9=K8*J9`)
  - SW개발비(부가세 별도) = 개발원가 + 이윤 + 직접경비 (`K11=SUM(K8:L10)`)
- FP당 단가: **605,784원** — 양식 `D7` 기재값(2024 가이드 표기). 2025 개정판 단가 미확인.
- 규모 보정계수: `0.4057 × (ln(FP) − 7.1978)² + 0.8878`, **500FP 미만 1.28, 3,000FP 초과 1.153** (양식 `K21` 수식)
- 애플리케이션 복잡도 보정계수 (양식 `(참조)보정계수` 표)
  - 연계복잡성: 1.없음 0.88 / 2.1~2개 0.94 / 3.3~5개 1.00 / 4.6~10개 1.06 / 5.10개 초과 1.12
  - 성능: 0.91 / 0.95 / 1.00 / 1.05 / 1.09
  - 운영환경 호환성: 0.94 / 1.00 / 1.06 / 1.13 / 1.19
  - 보안성(암호화·웹취약점 점검·시큐어코딩·개인정보보호 등 요구 수): 1가지 0.97 / 2가지 1.00 / 3가지 1.03 / 4가지 1.06 / 5가지 이상 1.08
- 이윤율: 양식 `J9` 입력칸 예시 **0.2**(1101·1102), 2101 양식 예시는 0.25. **공식 상한·기준 미확인** → 기본 0.2를 '양식 예시값(확인 필요)'로 표시, 사용자 수정 가능.
- 직접경비: 양식 별도 표(항목·산출내역·금액). 사용자 입력. 장비 구매비는 입력 대상 아님(경고).
- VAT: 10% (부가가치세법 세율). 다른 양식(1103·2201·2401 등)에서 `×1.1`(부가세 포함) 확인. 개발비 양식은 '부가세 별도'까지만 산출.
- 끝수 처리: 양식에 규칙 없음(원 미만 소수 그대로 둠). **미확인** → 사용자 설정(단위 1/10/100/1,000원, 절사/반올림). 기본값 '원 미만 절사'는 시스템 기본값이며 공식 근거 아님.
- 단계별 산정 범위(분석·설계·구현·시험): 가이드의 단계별 비율 **미확인**. 4단계 모두 포함 시 비율 1.0.
  일부 단계만 포함하면 사용자가 단계 비율을 입력해야 하며, 입력 전에는 견적을 '미확정'으로 표시한다.
  적용 위치: 개발원가 × (포함 단계 비율 합).

### 계산 순서와 끝수 (시스템 규칙, 2026-10-29 결정)
1. 모든 중간값은 Decimal(정밀도 28)로 계산하고 반올림하지 않는다(규모계수 ln 포함).
2. 개발원가·이윤은 표시용으로 끝수 규칙 적용: `개발원가R = round(개발원가)`, `이윤R = round(개발원가R × 이윤율)`
3. 개발비(VAT 별도) = 개발원가R + 이윤R + 직접경비(원 단위 정수)
4. VAT = round(개발비 × 0.1), 총액 = 개발비 + VAT
5. 엑셀은 같은 순서의 수식(ROUNDDOWN/ROUND)과 Python 확인값을 함께 둔다.

## 6. 목표예산 시나리오 (구현: `cost.py::target_scenario`) — 공식 산정 아님
- 기준 FP 항목·분류·가중치·총FP는 그대로 둔다. 시나리오는 기준 견적과 **동일한 FP 항목 ID 집합**을 가진다.
- 입력: 목표금액 T, VAT 포함 여부.
- 목표 공급가액 S_t: VAT 포함이면 `S + round(S×0.1) = T`를 만족하는 정수 S를 탐색(세율 방식).
  끝수 절사 때문에 그런 S가 없으면(예: 120,000,000원) **역산 방식**: `S_t = floor(T ÷ 1.1)`, `부가세 = T − S_t`.
  이때 세율 방식 부가세와의 차이(보통 ±1원)를 결과와 경고에 공개한다(`vat_method`, `vat_by_rate`, `vat_residual`).
- 목표 개발원가 C_t = (S_t − 직접경비) / (1 + 이윤율), 조정률 r = C_t / 기준 개발원가(반올림 전).
- 표시 방식(같은 r의 세 표현): 조정률 r, 예산 대응 환산 FP = 기준FP × r, 예산 대응 환산 단가 = 단가 × r.
  모두 '예산 대응 참고값(공식 측정값 아님)'으로 표시한다.
- 원 단위 일치: `C_tR = round(C_t)`, `P_tR = round(C_tR × 이윤율)`, `끝수조정 = S_t − (C_tR + P_tR + 직접경비)`를 별도 행으로 표시(숨기지 않음).
- 직접경비가 목표 공급가액보다 크면 오류. r < 1이면 '기준 산정보다 낮음 — 요구 기능 유지 시 공식 산정 금액에 미달' 경고.

### 4-1. DET·FTR/RET 근거 목록 집계 (시스템 규칙, 2026-10-30 — 공식 계수 규칙 원문 미확인)
비전문가가 숫자를 넣지 않도록, 사용자가 업무 말로 쓴 **항목 목록**에서 코드가 개수를 센다(`engine.derive_metrics`).
DET/FTR/RET 계수 규칙의 KOSA 가이드 원문은 확인하지 못했다. 아래는 IFPUG 일반 원칙을 단순화한 **시스템 규칙**이며, 결과는 '복잡도표(근거 목록 집계)'로 따로 표시한다(직접 입력값과 구분).
- 직접 입력(DET·FTR/RET 숫자)이 있으면 그 값을 쓴다(전문가 경로).
- DET: FP 항목의 `det_items` → (EI) 연결 기능의 입력 항목 / (EO·EQ) 입력+출력 항목 → (ILF·EIF) 연결 데이터의 주요 항목. 쉼표·세미콜론·줄바꿈·' 및 '·'/'로 나누고 중복을 뺀다. '확인 필요'·25자 초과 문장은 세지 않는다.
- FTR(EI/EO/EQ): 연결 데이터 ID 수.
- RET(ILF/EIF): **기본 묶음 1 + 추가 하위 그룹 수**(FP `ret_groups` → 데이터 `subgroups`). 데이터 이름과 같은 그룹은 기본 묶음으로 보아 빼다. 예: 신청 정보 + 승인 이력 → RET 2.
- 근거가 없으면 정통법은 '근거 부족'(점수 없음)이고, 이 메모는 정통법 칸(`detailed_note`)에만 둔다. 간이법 경고·상태에 섞지 않는다.
- AI가 준 DET·FTR 숫자는 저장하지 않는다(근거 목록만 받음).

### 4-2. 집계 근거와 산정 상태 (2026-10-30)
- 집계 근거(항목별 `count_basis`): **확정**(상태 '확정' = FP 기술 검토 완료) / **업무 확인**(`scope_confirmed`=예, 상태 초안·검토중 — 담당자가 '우리 사업에 있는 처리·자료'라고 답함) / 미집계.
  업무 확인은 FP 유형·복잡도를 확정한다는 뜻이 아니다. 업무 확인만으로 들어간 항목이 있으면 산정은 '추정'이다.
- 산정 상태(간이법·정통법 각각, `engine.estimate_basis`):
  - **미산정**: 집계 항목 0건 → 금액을 만들지 않는다(0원을 견적으로 보이지 않음).
  - **부분 산정**: 집계 밖에 업무 확인 전·미분류·중복 의심 후보, FP 미연결 기능 요구사항, (정통법) 근거 부족 항목이 남음.
  - **추정 산정**: 남은 후보는 없지만 업무 확인만 한 항목 또는 (정통법) 가정 복잡도가 포함됨.
  - **확정 산정**: 집계 항목이 모두 기술 검토 확정이고 남은 후보가 없음.
- 업무 확인에서 '없음'으로 후보를 모두 제외한 요구사항은 'FP 없음(후보를 제외로 결정)'으로 'FP 미연결'과 구분한다.
- 목표예산 시나리오는 기준 산정이 추정·부분이면 그 사실을 경고로 남긴다(조정 정책은 §6 그대로).

## 7. FP 식별 규칙(시스템이 표시하는 검증)
- 메뉴·화면·버튼·테이블 수를 FP 개수로 쓰지 않는다. 데이터 테이블은 사용자 관점 논리 데이터 그룹으로 묶어 ILF/EIF 판단.
- 측정 경계(`project.boundary_name`) 밖 애플리케이션의 EI/EO/EQ/ILF는 집계 제외 + '경계 확인 필요'.
  EIF는 다른 애플리케이션이 유지하는 데이터를 참조할 때만 해당.
- 같은 경계·유형에서 정규화한 이름이 같거나, '(관리자)/(사용자)' 등 역할 표기만 다른 항목은 '중복 의심'.
  같은 데이터가 ILF와 EIF로 동시에 있으면 '중복 의심'.
- 요구사항 중 기능 요구사항인데 연결된 FP가 없으면 'FP 미연결', 비기능은 'FP 대상 아님(검수 기준 관리)'.
- 집계는 §4-2를 따른다: 상태 '확정' 또는 업무 확인한 초안·검토중 항목만 들어가고, 업무 확인 전 후보는 집계 밖에 남는다.
- 중복 의심(2026-10-30 보완): 이름이 비슷하고(유사도 0.6 이상) 연결 기능·요구사항이 겹치면 표시한다. 단 '등록·수정·삭제·승인·반려·취소'처럼 처리 동사가 서로 다르면 별개 처리로 본다. 중복 의심이 풀리지 않은 항목은 집계하지 않는다.
- 후보 재실행: 기존·대기 중 후보와 같은 처리면 '갱신 변경안'(비어 있는 칸만 채움), 비슷하면 '추가하되 비슷함 표시'. 적용 시점에 이미 같은 항목이 있으면 'merged'로 처리하고 새로 만들지 않는다. 기존 항목은 자동 삭제하지 않는다.
- 한국어 산출물에 가나 문자나 한글 없는 한자 문장이 섞이면 AI에 한 번 다시 요청하고, 남으면 항목에 '다른 언어가 섞인 이름·근거' 표시(확인 목록 'FP 기술 검토 필요').
