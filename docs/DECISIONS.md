### D-019 (2026-10-30) 테스트 배포: Render 웹 서비스 1대 + 영속 디스크
- 지시: "신규개발 기능을 직접 사용해 검증할 수 있도록 테스트 배포 준비, 간단한 배포안 하나 추천."
- 선택: Render Web Service(Docker, Starter, Singapore) + 1GB 디스크(`/data`), 저장소 루트 `render.yaml`(Blueprint). 비밀값은 `sync: false`로 Render 화면에서만 입력, `SECRET_KEY`는 `generateValue`.
  - 이유: 현재 구조(이미지 1개 = 화면+API, SQLite, 작업 스레드)는 서버 1대 + 영속 디스크가 맞고, GitHub 연결·화면 입력만으로 HTTPS·비밀값·자동 재배포가 되어 명령줄 도구가 필요 없다.
  - 대안: Fly.io(더 저렴, flyctl 필요), 기관 VM + Docker. 무료 인스턴스는 디스크가 없어 제외.
- 이미지 변경: root로 시작해 `/data` 소유자를 맞춘 뒤 비루트로 전환(`docker-entrypoint.sh`, 배포 디스크가 root 소유일 때 기동 실패하던 문제), 포트는 `PORT` 환경변수(기본 8000).
- 실제 배포·과금은 사용자 결정(agent.md §12). Render 공식 문서는 이 세션 네트워크 정책으로 열지 못해, `render.yaml` 항목은 배포 시 Render 화면에서 확인한다(수동 설정 절차를 DEPLOY §3에 함께 둠).

### D-020 (2026-10-30) GitHub Pages 정적 시연판: 빌드 때 모듈 교체 + 생성기로 만든 정적 샘플
- 지시: "서버·API 키 없이 GitHub Pages에서 화면과 결과물을 둘러볼 수 있는 별도의 정적 시연 모드. 기존 화면 재사용, 빌드 시 명시적 선택, URL 파라미터로 인증 우회 금지, 금액·FP는 Python 엔진으로 생성·검증."
- 선택:
  - **빌드 모드 교체**: `vite build --mode demo`에서만 Vite 플러그인이 `src/api.ts`→`src/demo/api.ts`, `src/App.tsx`→`src/demo/DemoApp.tsx`로 바꿔 끼운다. 일반 빌드에는 시연 코드·데이터가 없고 런타임 플래그가 없어 인증 우회 경로가 생기지 않는다. 시연 API 어댑터는 실제 api.ts 타입(`typeof Real.api` 등)에 맞춰 화면 코드를 그대로 쓴다.
  - **읽기 전용은 공용 컴포넌트에서**: `Ctx.readOnly`(시연판만 설정) + `ActionButton`(비활성화·이유 툴팁)·`EditArea`(fieldset disabled)·`EditableTable` 추가·수정·삭제 숨김. 단계 화면을 복제하지 않는다.
  - **샘플 데이터는 생성기**: `backend/tools/demo_data.py`가 임시 DATA_DIR로 서버 앱을 띄워 실제 API(샘플 규칙 모드, AI 호출 없음)로 두 프로젝트를 만들고, 화면이 쓰는 GET 응답과 서버 엑셀 생성기 결과를 정적 파일로 저장. `--check`는 Project 모델 검증·FP 합계·견적 총액(당시 기준 스냅샷)·엑셀 표시·파일 해시를 현재 엔진과 비교. pytest(`test_demo_data.py`)로 CI에서도 확인.
  - **생성 결과는 커밋하지 않음**: agent.md §10(생성된 엑셀 커밋 금지)에 따라 `frontend/demo-public/demo-data/`는 .gitignore, Pages 워크플로가 빌드 단계에서 매번 생성·검증(Pages 런타임에서는 Python 실행 없음). 샘플이 엔진과 어긋날 수 없다.
  - **다운로드 파일 이름은 ASCII**(`SAMPLE-A_…xlsx`): 2026-10-30 확인 결과 헤드리스 Chromium이 한글 `download` 이름을 버리고 확장자 없는 `download`로 저장 — 파일 안(첫 시트 제목·속성)에 '샘플 시연판(가상 데이터)' 표시.
  - **배포**: 별도 `pages.yml`(main 푸시·수동 실행 배포, PR은 빌드·브라우저 확인만), `configure-pages@v6`·`upload-pages-artifact@v5`·`deploy-pages@v5`, deploy job만 `pages: write`·`id-token: write`, `github-pages` 환경, 동시 배포 그룹 `pages`.
- 함께 고친 것: 업체 문서에도 '분석이 끝나지 않은 문서' 안내가 뜨던 상태 표시(참고문서만으로 한정, 회귀 테스트), 참고 항목 '수정' 결정의 수정 후 문장 표시, 좁은 화면에서 넓은 표를 표 안 가로 스크롤로.

  - 단위를 10원 이상으로 골라도 총액은 공급가액+부가세를 더하기만 했다. 그래서 직접경비가 단위 배수가 아니면 총액이 단위 배수가 아니었다.
- 선택:
  - `Rounding.unit` 기본값을 10으로 바꿨다. 저장된 설정은 값을 그대로 읽는다(모든 저장 데이터에 unit이 명시되어 있어 재해석 없음).
  - `money_steps()`가 끝수 처리를 한 곳에서 한다: 개발원가·이윤·부가세 각각과 최종 총액.
    - 직접경비 입력액과 공급가액 합산은 그대로 둔다.
    - 차액은 `final_adjustment`(음수 가능)로 따로 기록하고, 화면·엑셀에 '최종 끝수조정(참고 조정)' 행으로 표시한다.
  - 견적 결과에 `rounding.policy = final-total-v2`, 적용 항목, 예시를 기록한다. 이 필드가 없는 이전 견적은 당시 방식으로 표시·출력한다.
  - 상태 해시에는 단위가 1이 아닐 때만 정책 버전을 넣는다. 원 미만 견적은 결과가 같아 '현재 데이터와 일치'를 유지하고, 10원 이상 이전 견적은 '갱신 필요'가 된다.
  - 목표예산 시나리오는 목표액 맞춤(참고 정책)을 그대로 쓴다. 목표액이 단위 배수가 아니면 충돌을 경고하고(`unit_conflict`) 목표액은 고치지 않는다. 조정 행 이름은 '목표액 맞춤 끝수조정(참고)'이다.
- 채택 안 함:
  - 공급가액 자체에 끝수 처리 적용(직접경비 원금이 바뀌어 보이는 혼동).
  - 기존 견적 금액 일괄 재계산.
  - 차액을 VAT·이윤에 흡수.
- 남은 확인: 기관·계약 기준의 끝수 규정, 최종 끝수조정의 세무상 취급(미확인).

### D-028 (2026-11-06) 로그인 실패 제한을 접속자별로: 신뢰할 프록시 단 수를 배포에서 선언
- 지시: "프록시 뒤에서 한 사람의 오타 5회가 다른 심사위원까지 막는 문제를 고쳐라. `FORWARDED_ALLOW_IPS=*`를 일괄 적용하거나 클라이언트가 보낸 `X-Forwarded-For`를 그대로 신뢰하지 말고, 기존 실패 제한은 유지하라."
- 원인:
  - 제한 키가 `request.client.host`였다. 리버스 프록시 뒤에서는 이 값이 프록시 주소라서 모든 접속자가 한 키로 묶인다.
  - `Dockerfile`이 `--proxy-headers`를 주지만 uvicorn의 `forwarded_allow_ips` 기본값이 `127.0.0.1,::1`이라 프록시가 비루프백이면 헤더가 무시됐다.
  - 심사 기간에는 여러 심사위원이 같은 관리자 비밀번호로 접속하므로 공용 잠금이 곧 심사 중단이 된다.
- 확인하지 못한 것: Render의 프록시 단 수와 `X-Forwarded-For` 처리 방식. 공식 문서에 없고, 벤더 발언("첫 번째 값이 실제 접속자")과
  커뮤니티 보고("프록시가 기존 헤더를 지우지 않고 오른쪽에 덧붙이기만 한다")가 서로 어긋난다. 그래서 **왼쪽 값은 신뢰하지 않는다**.
- 선택:
  - `auth.client_ip(peer, xff, hops)`: `X-Forwarded-For`를 **오른쪽에서** `hops`번째 값으로 접속자를 식별한다.
    바로 연결된 프록시만 오른쪽에 덧붙일 수 있으므로 클라이언트가 왼쪽에 값을 끼워 넣어 제한을 피할 수 없다.
    체인이 `hops`보다 짧으면 `peer`로 되돌린다(위조로 새 키를 만들 수 없다).
  - `TRUSTED_PROXY_HOPS` **기본 0**(헤더 불신). 직접 노출·로컬·Windows 시험판에서 안전하다.
    0이 아닌 값은 프록시 뒤 배포에서만 '선언'한다 — `render.yaml`에 `1`.
    기본값을 1로 두면 직접 노출된 서버에서 접속자가 헤더를 바꿔 새 키를 만들어 제한을 피할 수 있어 채택하지 않았다.
  - `Dockerfile`은 `--no-proxy-headers`로 바꿨다. uvicorn이 '맨 왼쪽'(위조 가능한 값)으로 `client.host`를 덮어쓰지 않게 하고,
    접속자 식별을 `client_ip` 한 곳에서만 처리한다. 앱은 `request.url.scheme`을 쓰지 않아 영향이 없다(`COOKIE_SECURE`는 환경변수).
  - 실패 제한 자체(5회/5분)는 바꾸지 않았다.
  - `/api/system`에 `client` 진단값(`peer`, `forwarded_count`, `trusted_proxy_hops`, `login_throttle_key`, `shared_key_warning`)을 더했다.
    배포 후 **운영 서버에서 일부러 잠금을 만들지 않고** 프록시 단 수를 확인할 수 있다(`docs/DEPLOY.md` §4-1).
- 채택 안 함:
  - `FORWARDED_ALLOW_IPS=*` 또는 맨 왼쪽 XFF 신뢰(위조로 제한 우회 가능).
  - Cloudflare `True-Client-IP`·`CF-Connecting-IP`(Render가 전달한다는 공식 근거를 확인하지 못함).
  - 하드 차단을 지연(backoff)으로 바꾸기(기존 실패 제한을 유지하라는 지시 범위를 넘음).
- 남은 확인: **실제 Render에서의 프록시 단 수**. `render.yaml`의 `1`은 최소값이며, 2단이면 키가 프록시 주소로 묶여
  수정 전과 같은 공용 잠금이 된다(위조는 여전히 불가). 배포 후 `docs/DEPLOY.md` §4-1로 확인해 값을 맞춘다.

### D-029 (2026-11-06) API 응답에 `charset=utf-8` 명시 — 브라우저에서 한글이 깨지던 문제
- 발견: 사용자가 배포 점검 절차(`docs/DEPLOY.md` §4-1)대로 `https://<주소>/api/system`을 브라우저에 입력했더니
  `{"detail":"濡쒓렇�몄씠 �꾩슂�⑸땲��"}`로 보였다. UTF-8 한글 바이트를 CP949로 읽은 결과다.
- 원인: 모든 JSON 응답이 `Content-Type: application/json`이고 **charset 파라미터가 없었다**.
  JSON은 규격상 UTF-8이고 화면 코드(`fetch` → `response.json()`)는 항상 UTF-8로 읽어 앱 동작에는 문제가 없다.
  그러나 **사람이 API 주소를 브라우저에 직접 열면** 브라우저가 문서로 렌더링하며 인코딩을 추측하고,
  한국어 Windows에서는 CP949로 읽어 한글 메시지가 깨진다. 점검 절차가 바로 그 경로를 쓰게 하므로 드러났다.
- 선택:
  - `main.JsonUTF8`(media_type `application/json; charset=utf-8`)을 만들고 FastAPI `default_response_class`로 지정했다.
  - 직접 만드는 응답도 모두 교체: 미들웨어 401·403, 사용자 예외 핸들러 8종, 로그인 401, 없는 API 404.
  - 프레임워크 내장 핸들러(`StarletteHTTPException` 404·405, `RequestValidationError` 422)도 같은 클래스로 덮었다.
    본문 형식은 기본값과 같게 유지했다(`{"detail": …}`, 검증 오류는 `jsonable_encoder(e.errors())`).
- 함께 고친 것: `/api/system`에서 `{"detail":"로그인이 필요합니다."}`가 나오는 것은 **정상 동작**(미로그인)이라는 설명과,
  쿠키가 `SameSite=strict`이라 주소창에 직접 입력해야 한다는 점을 `docs/DEPLOY.md` §4-1에 적었다.
- 채택 안 함:
  - 점검용으로 `/api/system`을 인증 없이 열기(진단값에 접속 주소가 들어가고, 미로그인 API 차단 원칙을 깨뜨림).
  - 응답 본문을 ASCII로 escape(한글 가독성을 버림).
- 남은 확인: 실제 Render 배포본에서 브라우저로 한글이 정상 표시되는지(이 세션은 배포 주소에 접속할 수 없음).
