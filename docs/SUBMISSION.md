## 3. 제출 버전 고정 절차
Render는 연결된 브랜치(main)에 커밋이 들어오면 기본 설정상 자동으로 다시 배포합니다. 제출 뒤 main이 바뀌면 심사 중 서버가 제출 코드와 달라질 수 있습니다.
이번 작업에서는 자동배포 설정을 바꾸지 않았습니다. 아래는 제출 시점에 사용자가 고를 절차입니다.

1. 제출할 내용이 모두 main에 병합되었는지 확인하고, CI(테스트·E2E)가 통과한 커밋을 고릅니다.
2. 그 커밋에 태그를 붙입니다(예: `submission-2026-11-11`).
   ```bash
   git tag -a submission-2026-11-11 -m "세션1 제출 버전" <커밋>
   ```
   ```bash
   git push origin submission-2026-11-11
   ```
3. GitLab에 올린 커밋 ID가 태그 커밋과 같은지 확인합니다.
4. Render 화면(서비스 → Events)에서 마지막 배포의 커밋 ID가 같은지 확인합니다. 앱에는 버전 표시 API가 없어 Render 화면으로 확인합니다.
5. 심사 기간(예선·본선) 동안 다음 중 하나를 택합니다(사용자 결정).
   - main에 병합하지 않기(작업은 다른 브랜치에서만), 또는
   - Render의 자동배포를 끄고 필요 시 수동 배포.
6. 심사 중 서버 재시작·디스크 유지 상태, AI 사용료 한도를 확인합니다. 무료 인스턴스는 재시작 때 데이터가 지워지므로 `render.yaml`은 Starter + 디스크 기준입니다.

## 5. 세션 1 평가 항목별 근거와 한계
배점은 사용자 요약 기준입니다. 효과 수치(시간 단축률 등)는 측정하지 않았으므로 쓰지 않습니다.

| 항목(배점) | 현재 구현으로 보여 줄 근거 | 한계(그대로 밝힐 것) |
|---|---|---|
| 필요성(20) | 대상이 설계·FP 비전문가 공무원이라는 설정, 전문용어 없이 업무 질문으로 진행, FP·개발비·과업지시서·엑셀을 한 흐름으로 연결 | 실제 공무원 사용자 시험·현장 수요 조사는 하지 않음 |
| 창의성(30) | AI는 질문·초안·후보만, 가중치·금액·검산은 코드. 업무 확인(있음/없음/모름)과 FP 기술 검토 분리, 미산정·부분·추정·확정 표시, 기준 산정과 목표예산 시나리오 분리, 참고문서의 타 기관 고유 조건 표시 | 개별 요소의 독창성 비교 조사는 하지 않음 |
| 활용성(20) | 웹 브라우저만으로 사용, AI 키 없이도 샘플 모드로 전 단계, 산출내역서형 엑셀(A4 인쇄), 기존 업체 문서 검토 | 단일 관리자 로그인, 다중 사용자·권한 없음, HWP 실험적, OCR 없음, Microsoft Excel 화면 미확인 |
| 완성도(15) | 백엔드 테스트·E2E(흐름·참고문서·UX·예제·시연판)·검산 시트, 실행 기록 [VALIDATION](VALIDATION.md) | KOSA 가이드 원문 미확인(산정양식 수식에서 추출), 이윤율·끝수 등 '확인 필요' 항목, 실제 사업 데이터 검증 없음, AI 결과는 실행마다 달라짐 |
| 확산가능성(15) | Docker 단일 이미지, AI 공급자 교체 구조(OpenAI·Anthropic·OpenAI 호환 사내 LLM), 기준값 버전별 설정 파일, 유지관리 등 사업 유형 확장 여지 | 실제 호출 확인은 OpenAI뿐(나머지는 연결 코드·모의 시험), 이번 범위는 신규개발 2종, 기관 망 반입·보안 심사는 하지 않음 |

## 6. 로그인 정보 전달
- 실제 앱은 관리자 비밀번호 하나로 로그인합니다. 값은 Render 환경변수 `ADMIN_PASSWORD`에만 있고 저장소·문서·영상에 넣지 않습니다.
- 공고가 정한 경로로만 전달합니다(신청서 기재란·별도 전달 등).
- 심사가 끝나면 비밀번호를 바꾸는 것을 권장합니다. 바꾸면 기존 로그인은 쿠키 만료 전까지 유지될 수 있으므로 `SECRET_KEY`를 함께 바꾸면 즉시 무효화됩니다.
- 인증을 끄거나 공개 비밀번호를 두는 방식은 쓰지 않습니다.
